# 09 - Authoring status, the test loop, open questions, next steps

## Can we author a track? Current answer
The gameplay-critical structures can be generated from scratch and the generators are proven against SEGA's data
byte for byte (road, AI map, container). The scenery tree can be generated in a minimal form (proven structurally
only). Wall collision cannot be generated yet but can be left out. Nothing has been run in the game.

## What the flat test loop contains (work/out/step8_flat_loop, script work/scripts/build_testtrack.py)
AUTHORED (generated by the script from numbers):
- road: 1000 slices, flat oval (straights 311.5 m, radius 60 m), 14 m wide, y = 0, centre x=0 z=450
- height blob (all 0xBF), overlay page table (1 page), two 32x32 page textures (pixels authored, header borrowed)
- checker pixels of the two surface-layer textures actually used (ids and headers kept: the id selects the surface type)
- scenery tree: 83 nodes / 50 leaves under the road, no meshes, all-visible streams, no light map
- AI map: 1976 cells, 8 lanes
- start line (slice 100), direction +1, start grid (Lakeside pattern), spline with 501 points + 2 split markers
- master_gfx root edits: boundary pointer/ref cleared
BORROWED unchanged from the user's Stadium4 (or Desert4 for the Desert build):
- sky dome mesh, its materials/shader/textures; the lighting objects; the two small root textures
- vertex pattern of a road cell (surface indices, weight word, batch record) - copied from the most common cell
- trackside camera lists, kind 12 glue objects, Stadium's extra chunk at root +0x28
- game_objects, gameobj_dis, pobj_master, pobj_plac files and the grass cache (objects stay at their old positions,
  which is why the loop is placed 300 m away from them)
- every material/texture in master_gfx that the pobj files reference
The built folders therefore contain SEGA data and must not be redistributed.

## Honest estimate
- step0/step1 (container): expected to work (identical data; alignment rules observed on all files).
- step2 (AI map): loads; AI quality unknown.
- step3 (no walls): loads per the null check; edge behaviour unknown.
- step4 (authored scenery tree): about even odds. Risks: something expecting a light map, instance lists or
  meshes of material type 6; boxes that are exact instead of loose.
- step5 (uniform road surface): likely works; risk in the batch-record/weight convention and the 32x32 page.
- step6 (spline added to Stadium): likely works.
- step7/8 (authored loop): each piece may pass alone and the sum still fail. Most likely failure points, in order:
  1. scenery tree (as step4);
  2. start/direction: Stadium4 runs with direction -1 and start slice 0 and a special first grid entry; we use
     +1 / 100. Stadium4 may not be a normal race slot at all (no spline, 217-frame animation chunk) - hence the
     Desert4 build;
  3. no boundary walls + nothing outside the 14 m road;
  4. borrowed cameras/objects far from the road (replay or intro cameras looking at empty space; harmless if lucky);
  5. uniform-width road: SEGA's slices always have fractional edge columns - ours are whole metres (should be fine).
Overall chance that step8 loads to a drivable grid at the first attempt: roughly 35-45%; that the ladder pinpoints
the failing piece if it does not: high.

3. Surface type per texture id: dump the id lists behind 0x5B1820 (data base at [0x9DB80C], probably
   `\SurfacePairEffects\surfacepairdata_xdata`) to name the surfaces.

5. Meaning of the three AI lane-mask sets; root fields +1C, +20, +24, +80..+94; slice +7C (water?), +80, +84.

7. Variable-width roads: rules for +6E/+6F/B are verified, but the builder input for changing widths
   (extra duplicated vertices) is only exercised through SEGA's own data.
8. Is the track really closed-circuit only? All six are; point-to-point (Revo stages) not examined.
